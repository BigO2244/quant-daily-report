# Validation Isolation Policy

## Purpose

FR-020 defines read-only validation isolation semantics for Caerus tests, smoke
checks, and bounded operator diagnostics.

This policy is governance only. It does not change test code, runtime producers,
cron, broker behavior, execution workflows, dashboard publishing, or artifact
cleanup behavior.

## Problem

Some tests and smoke checks can create files under repo-level `outputs/` or
`logs/` paths that look similar to production runtime evidence. Without clear
isolation rules, operators may confuse validation residue with canonical
artifacts or stale operational state.

The goal is not to stop validation. The goal is to make validation evidence
clearly separate from production evidence.

## Isolation Principles

- Validation outputs are not production evidence unless explicitly promoted by
  an incident review.
- Tests should prefer temporary roots, fixtures, or bounded `/tmp` directories.
- Smoke checks should state whether they are read-only, dry-run, or writing
  bounded validation output.
- Validation should not overwrite dated production runtime artifacts.
- Validation residue should not be consumed by dashboards, packets, promotion
  review, broker reconciliation, or source-readiness checks.
- Future isolation tooling should fail visibly rather than silently writing into
  production-like paths.

## Output Classes

| Class | Meaning | Preferred Location | Operator Use |
|---|---|---|---|
| `unit_test_fixture` | Synthetic inputs created by tests. | `tmp_path`, test fixture directories. | Test-only. |
| `bounded_smoke_output` | Output from a manual validation command. | `/tmp/<caerus-validation-name>/` or clearly named non-canonical directory. | Review command behavior, not system state. |
| `read_only_diagnostic` | Terminal or JSON output generated by inspecting existing artifacts. | stdout or explicit diagnostic file outside canonical runtime paths. | Operator interpretation. |
| `production_runtime_evidence` | Artifacts produced by scheduled or approved runtime workflows. | Canonical `outputs/` or deployed runtime paths. | Operational evidence. |
| `incident_evidence_copy` | Preserved copy of runtime evidence for investigation. | Dated/path-scoped backup location. | Incident review only. |

## Bounded Validation Rules

Use bounded validation output when a command must write files for verification.

Required properties:

- explicit destination path;
- no dependency on broker credentials or order submission;
- no writes to canonical runtime trade-date directories unless the task is a
  governed runtime recovery;
- no mutation of `latest` publications unless the validation is explicitly about
  publication behavior and uses a temporary root;
- no cleanup of production artifacts as part of the validation;
- validation summary should identify the output root.

Recommended examples:

- `/tmp/caerus_orion_validation/`
- `/tmp/caerus_packet_validation/`
- `/private/tmp/caerus_research_clarity_validation/`

Avoid using:

- `outputs/runs/<live-run-id>/`;
- `outputs/broker/`;
- `outputs/precompute/<today>/`;
- `outputs/shadow_candidates/latest/`;
- deployed dashboard directories;
- VM cron-owned log paths for local tests.

## Read-Only Diagnostic Rules

Read-only diagnostics may inspect production artifacts when the command does not
write or mutate state. These commands should still print:

- inspected trade date or latest source date;
- artifact paths inspected;
- readiness or health status;
- blocking reasons;
- recommended next action.

Read-only diagnostics are allowed to run on the VM during market hours when they
do not touch broker state, cron, execution workflows, or dashboard deployment.

## Future Test Harness Requirements

Future code-level FR-020 work, if needed, should:

- parameterize repo roots in tests;
- prefer `tmp_path` fixtures for artifact-producing functions;
- add assertions that smoke validations write only to caller-provided output
  roots;
- keep fixture artifacts small and deterministic;
- avoid requiring network, broker credentials, cron, or live market state;
- document any unavoidable validation residue.

## Operator Guidance

When reviewing a validation result, first ask:

1. Was the command read-only?
2. If it wrote output, where was the bounded output root?
3. Could any generated file be mistaken for production evidence?
4. Did the command touch broker, cron, workflow, dashboard, or promotion paths?
5. Is any residue worth preserving as incident evidence?

If the answer is unclear, stop before cleanup or deployment and preserve the
current git status plus the validation output root.

## Relationship To Retention

FR-019 defines retention and backup semantics. FR-020 defines isolation
semantics. Together they mean validation residue should be easy to identify,
safe to ignore operationally, and safe to clean only after the operator confirms
it is not incident evidence.
