# Registry Invariants v1 — Caerus MCP Metadata Registry

**Spec ID:** SEM-REGISTRY-v1
**Version:** v1
**Date:** 2026-05-21
**Status:** Canonical
**Normative Language:** RFC 2119
**Frozen Under:** `SEMANTIC_FREEZE_v1.md`

---

## 1. Purpose

The MCP metadata registry (architecture §10) is the operational
materialisation of the Semantic Contract Layer. This document specifies
the **hard invariants** the registry MUST satisfy at all times.

The registry MAY be implemented in SQLite, in-memory structures, or any
other store; this specification governs the **semantic guarantees**
the implementation MUST preserve regardless of storage choice.

Failure of any invariant in this document is, by definition, a
correctness failure of the registry and MUST be raised as a finding —
not silently tolerated.

---

## 2. Object Identity Guarantees

### 2.1 Determinism

The registry MUST guarantee that, given the same `(object_type,
identity, schema.schema_version)` inputs, the same `object_id` is
generated by every conformant producer (SEM-001 §5).

The registry MUST NOT accept two distinct envelopes claiming the same
`object_id` with differing identity fields. Such a collision is a
violation and MUST be raised as `IDENTITY_COLLISION` finding (severity
`CRITICAL`).

### 2.2 Stability Across Rebuilds

The set of `object_id`s in the registry MUST be invariant under a
from-scratch rebuild from unchanged source. Rebuild that produces a
different identity set indicates either:

- A non-deterministic identity function (P-001 violation), or
- A source-substrate mutation between rebuilds.

Either case MUST be detected and surfaced as
`REGISTRY_REBUILD_DIVERGENCE` finding.

### 2.3 Uniqueness Surfaces

| Field | Uniqueness Scope |
|---|---|
| `object_id` | Unique within `(object_type, identity)` tuple; one canonical (non-superseded) instance per tuple at any moment. |
| `lineage.node_id` | Globally unique across the corpus (SEM-001 §5). |
| Schema `(schema_id, schema_version)` | Globally unique within the schema registry (SEM-008 §2). |
| `GovernanceFR.fr_id` | Globally unique within the FR registry. |

The registry MUST index every uniqueness surface for O(log n) lookup.

## 3. Deterministic Hydration Guarantees

Hydration is the act of reconstructing a full envelope from registry
state.

### 3.1 Faithful Hydration

For any `object_id` in the registry, hydration MUST produce an envelope
**byte-identical** (modulo SEM-003 §3.4 encoding) to the envelope last
ingested for that id.

If hydration cannot be performed (e.g., source artifact unreachable),
the registry MUST return `HYDRATION_FAILED` and identify the missing
component — it MUST NOT return a partial envelope as if complete.

### 3.2 Hydration Validation

Hydration MUST run the full validator chain (SEM-CONFORMANCE-v1 §4) on
every emitted envelope. Non-conformant objects MUST be refused at
hydration and surfaced as findings — not served as data.

### 3.3 Hydration Cache Discipline

The MCP MAY cache hydrated envelopes for performance.

- The cache MUST be invalidated when any of the following change:
  - The source artifact's content (detected via hash or `mtime`).
  - The schema version published for the artifact's type.
  - The governance state of any covering FR.
  - A `ConfidenceAssessment` enters or leaves validity at present.
- Stale cache reads MUST NOT be returned as fresh.
- The cache MUST NOT be the substrate for a registry rebuild.

## 4. Registry Rebuild Guarantees

### 4.1 Rebuildability

The registry MUST be rebuildable from source (storage substrate +
producers + governance source + Semantic Contract Layer) without
reference to the prior registry state.

Implementations MUST NOT introduce any registry-only state that cannot
be re-derived from source. The registry is a **derived artifact**;
durable institutional state lives in the substrate.

### 4.2 Rebuild Determinism

Two successive from-scratch rebuilds from identical inputs MUST produce
byte-identical registries (modulo storage-encoding noise that does not
affect semantic queries).

### 4.3 Rebuild Verification

The MCP audit subsystem MUST be able to perform on-demand:

- A from-scratch shadow rebuild.
- A diff against the current incremental index.
- A finding (`REGISTRY_INCREMENTAL_DRIFT`) for every discrepancy.

The shadow rebuild MUST be performable in bounded time appropriate to
the corpus size; performance is implementation-defined, but
verifiability is mandatory.

## 5. Lineage DAG Guarantees

### 5.1 Acyclicity

The registry MUST refuse any edge insertion that would introduce a
cycle in the lineage DAG (SEM-003 §2.2). Cycle detection MUST run on
every ingest pass.

### 5.2 Edge Type Closure

The registry MUST accept only edges whose type appears in the closed
edge-type sets:

- Provenance edges: `DERIVED_FROM | SUPERSEDES | REPAIRS`
  (SEM-003 §2.1).
- Governance edges: `GOVERNED_BY | VALIDATED_BY | AUDITED_BY |
  PROMOTED_FROM | FR_DEPENDS_ON | FR_COVERS | AUDIT_FINDS |
  AUDIT_BLOCKS | DEPLOY_INCLUDES | ROLLBACK_REVERSES |
  TRANSITION_CAUSED_BY` (SEM-003 §2.1 + SEM-004 §8.2).

Untyped or unknown-type edges MUST be refused at ingest.

### 5.3 Edge Immutability

Edges are append-only. The registry MUST NOT support edge deletion.
Corrections require `SUPERSEDES` edges and `AuditFinding` records
(SEM-003 §2.3, §6).

### 5.4 Parent Reachability

For every non-raw object in the registry, every entry in
`lineage.parent_refs` MUST resolve to a node already in the registry,
or the object MUST be rejected at ingest.

Forward references (parent not yet ingested) MUST be deferred and
re-evaluated; persistently unresolved references after a full rebuild
MUST be surfaced as `LINEAGE_DANGLING_PARENT` findings.

### 5.5 Traversal Bounds

The registry MUST support upstream and downstream traversal in time
bounded by the size of the relevant subgraph, not by the total corpus.
Queries that do not satisfy this bound MUST be refactored before
implementation.

### 5.6 Chain Hash Verification

Every object MUST carry a `lineage.transformation_chain_hash` computed
per SEM-003 §9. The registry MUST verify chain hashes at ingest and
re-verify on hydration.

A chain-hash mismatch MUST be raised as
`CHAIN_HASH_INCONSISTENCY` finding (severity `CRITICAL`).

## 6. Confidence Propagation Guarantees

### 6.1 Stamped vs Computed

The registry MUST store, for every object:

- The **stamped** confidence as emitted by the producer.
- The **recomputed** confidence at ingest, using SEM-007 §3 algebra.

If stamped ≠ recomputed, the registry MUST refuse the object and raise
`CONFIDENCE_STAMP_MISMATCH` (severity `HIGH`).

### 6.2 Chain Reporting

The registry MUST be queryable for the confidence chain of any object:

- The limiting component (surface, governance, propagation, trigger).
- The limiting parent (when propagation-bound).
- The set of triggered downgrade codes.
- Any active `ConfidenceAssessment` references.

A query that returns the bare `confidence.level` without the chain is
non-conformant (SEM-007 §8).

### 6.3 Reassessment Application

Active `ConfidenceAssessment` records MUST be applied at retrieval, not
silently baked into stored objects. The stored confidence remains the
production-time stamp; the retrieved confidence MAY differ when an
active assessment applies.

### 6.4 Reassessment Validity

A `ConfidenceAssessment` is **active at time T** if and only if:

- `temporal_validity.valid_from <= T`, AND
- (`temporal_validity.valid_to` is null OR `temporal_validity.valid_to
  >= T`), AND
- The assessment has not been superseded or invalidated.

Retrieval MUST apply only active assessments. Expired or superseded
assessments MUST be ignored for current queries (but remain queryable
for point-in-time history).

## 7. Truth-Surface Enforcement Guarantees

### 7.1 Surface Stamping

Every NAV-bearing object in the registry MUST carry
`surface.nav_surface_type`, `surface.execution_realism`, and
`surface.chain_status`. Absence at ingest MUST trigger `M007` refusal.

### 7.2 Compatibility Matrix Application

The registry MUST encode the SEM-002 §3 matrix as a queryable
relation. Tools requesting cross-object operations MUST consult the
matrix; the registry MUST be capable of answering "is op O permitted
across surfaces (S1, S2)?" with one of `COMPATIBLE`, `CAUTIOUS_OK`,
`INCOMPATIBLE`.

The matrix is closed (3×3 at v1). New surfaces require a v2 amendment
(SEM-FREEZE-v1 §13).

### 7.3 Override Recording

Every surface override MUST be recorded as an envelope annotation:

```json
"annotations.surface_override": {
  "rationale": "...",
  "audit_ref": "<audit_or_fr_id>",
  "override_severity": "HIGH"
}
```

The registry MUST refuse to apply an override absent both
`rationale` and `audit_ref`. The registry MUST downgrade the resulting
object's confidence to `LOW`.

### 7.4 Chain Status Propagation

When a parent object has `chain_status` in `{NO_PRIOR, BROKEN_CHAIN,
REPAIRED}`, the corresponding downgrade trigger (`CHAIN_NO_PRIOR`,
`CHAIN_BROKEN`, `CHAIN_REPAIRED`) MUST be applied to any NAV-bearing
child on the same surface and strategy. The registry MUST detect and
stamp this at ingest.

## 8. Staleness Semantics

### 8.1 Threshold Stamping

`temporal.staleness_threshold_seconds` is producer-set (SEM-001 §7).
The registry MUST persist the producer's value verbatim.

### 8.2 Derived Staleness

`temporal.is_stale` is **computed at hydration**, not stamped at
production (SEM-001 §7.5). The registry MUST evaluate:

```
is_stale = (now() - temporal.as_of) > staleness_threshold_seconds
```

at every hydration. A stored `is_stale` value (if any) MUST be
considered presentational only — the authoritative value is recomputed.

### 8.3 Staleness Downgrade

When `is_stale = true` at evaluation, the registry MUST apply the
`STALE` downgrade trigger (SEM-007 §5) at retrieval, lowering the
served confidence by one lattice level.

### 8.4 Staleness in Point-in-Time

For point-in-time queries, staleness is evaluated **relative to
`T_anchor`**, not present time:

```
is_stale_at_anchor = (T_anchor - temporal.as_of) > staleness_threshold_seconds
```

The registry MUST surface this distinction in the response.

## 9. Orphan Handling

### 9.1 Definition

An orphan is any non-raw object with empty `lineage.parent_refs`
(SEM-003 §4).

### 9.2 Refusal at Ingest

The registry MUST refuse silent orphan admission. Every orphan MUST be
surfaced as `ORPHAN_DERIVATION` finding (severity `HIGH`).

### 9.3 Retention Path

An orphan MAY be retained only if accompanied by an `AuditFinding`
documenting why parent recovery is impossible. Retained orphans MUST
carry `confidence.level = LOW` regardless of payload quality.

### 9.4 Apparent Orphans (Grandfathered)

For grandfathered artifacts (SEM-001 §11), the registry MAY attempt
parent inference via path-to-ontology mapping (architecture §12), MUST
record inferred edges with `transformation = "mcp.ingestion.inferred"`
and `deterministic = false`, and MUST cap inferred-chain confidence at
`LOW`.

### 9.5 Orphan Tracking

The registry MUST report, on demand, every orphan in the corpus along
with its inference history and any covering AuditFinding. Orphan
counts MUST be a first-class governance health metric.

## 10. Supersession Semantics

### 10.1 Single Canonical Per Tuple

For every `(object_type, identity)` tuple, exactly one object MUST be
the **canonical (non-superseded) instance** at any moment of present
time. The registry MUST enforce this invariant.

### 10.2 Supersession Recording

A supersession MUST be recorded as:

- A new object with the same identity tuple and a later `as_of`.
- A `SUPERSEDES` edge from the new object to the prior object.
- A non-empty `transformation` on the edge citing the governing
  reference (SEM-003 §8).

The prior object's `is_superseded = true` flag MUST be set in the
registry index. The prior object MUST NOT be deleted from storage.

### 10.3 effective_at

Supersession MUST carry `effective_at` (defaulting to the new object's
`as_of`). For supersessions taking effect on a delayed schedule,
producers SHOULD set `effective_at` explicitly (SEM-006 §6).

### 10.4 Point-in-Time Supersession Resolution

For a query at `T_anchor`:

- Among the supersession chain `O1 ← O2 ← ... ← On`, the canonical at
  `T_anchor` is the latest `Ok` with `effective_at <= T_anchor`.
- The registry MUST resolve this correctly without consuming
  post-anchor information.

### 10.5 Forbidden Ad-Hoc Supersession

A `SUPERSEDES` edge without a governing reference is non-conformant
(SEM-003 §8.5). The registry MUST refuse such edges at ingest and raise
`UNGOVERNED_SUPERSESSION` finding.

## 11. Temporal Integrity Guarantees

### 11.1 Monotonicity

For every supersession chain, `as_of` MUST be monotonically
non-decreasing. The registry MUST refuse insertion of a new object with
earlier `as_of` than an existing canonical for the same identity tuple
(such insertions imply backdating, which is forbidden).

### 11.2 produced_at ≤ as_of

Every object MUST satisfy `provenance.produced_at <= temporal.as_of`.
Producers stamp `as_of` as the wall-clock production instant; producers
that emit `produced_at > as_of` are buggy and MUST be refused (`M011`).

### 11.3 UTC Discipline

Every instant in the registry MUST be UTC ISO-8601 with explicit `Z`
or `+00:00`. Local-time stamps MUST be refused at ingest.

### 11.4 indexed_at

Every object MUST carry an `indexed_at` timestamp (the wall-clock
instant the MCP ingested it). `indexed_at` MUST satisfy
`indexed_at >= produced_at`, and the registry MUST maintain it as
authoritative — it MUST NOT be backdated.

### 11.5 Visibility (Discoverability)

For point-in-time queries, the admissibility test is:

```
min(temporal.as_of, indexed_at) <= T_anchor
```

(SEM-006 §8). An artifact that existed but was not yet indexed at
`T_anchor` MUST be fenced out even if its `as_of <= T_anchor`.

### 11.6 No Backfill

The registry MUST NOT accept retroactive `as_of` or `indexed_at`
modifications. If a correction is required, supersession is the only
mechanism.

## 12. Invalidation Conditions

The registry MUST treat each of the following as invalidation triggers
and propagate them per SEM-003 §6:

| Trigger | Effect |
|---|---|
| Parent `AuditFinding` of severity `HIGH` or `CRITICAL`. | Floor child confidence at `LOW`; stamp `annotations.provenance_invalidated = true`. |
| Parent surface label correction. | Re-derive child surface; supersede if incompatible. |
| Parent schema MAJOR migration. | Re-derive child under new schema; supersede old child. |
| Governing FR rollback. | Recompute child's `governance.state` and inheritance chain. |
| Detection of future-information contamination upstream. | Invalidate downstream; floor confidence at `UNAVAILABLE` where the contamination is material. |

Invalidation MUST propagate downstream only; it MUST NOT alter parents.

### 12.1 Invalidation Persistence

Invalidated objects MUST remain queryable. The registry MUST maintain
`is_invalidated`, `invalidation_finding_ref`, and `invalidated_at`
fields per object.

### 12.2 Invalidation Audit Trail

Every invalidation event MUST be recorded as an `AuditFinding` with
the full set of affected `object_id`s. The registry MUST be queryable
for "what was invalidated and why?" by finding id, date range, or
strategy.

## 13. Conditions That Invalidate Registry Correctness

The following conditions render the entire registry **non-canonical**
and MUST trigger emergency rebuild:

1. Successful insertion of a cycle in the lineage DAG (an
   ingest-layer bug).
2. Two `object_id`s with identical identity but distinct content
   accepted into the canonical (non-superseded) set.
3. A canonical object whose stamped confidence exceeds the recomputed
   floor without an active `ConfidenceAssessment`.
4. A `SUPERSEDES` edge without a governing reference.
5. A `governance.state = GOVERNED_*` object with empty `governing_frs`
   accepted.
6. A NAV-bearing object without surface labels accepted.
7. A point-in-time query returning post-anchor inputs in its result.
8. A registry shadow-rebuild diff containing semantic differences.
9. Detection of in-place schema-version reuse without bump.
10. Detection of a closed-enumeration value not in the v1 set.

Each of these MUST raise `REGISTRY_CORRECTNESS_VIOLATION` (severity
`CRITICAL`), suspend new ingest, and trigger remediation under the
audit process. The registry MUST NOT continue serving data with known
correctness violations of this class.

## 14. Required Validation Tests

A conformant registry implementation MUST ship with — and pass — a
test suite covering at minimum:

| Test Class | Verifies |
|---|---|
| Identity collision | Distinct identities cannot share `object_id`; collisions raise findings. |
| DAG acyclicity | Cycle insertion is refused. |
| Edge type closure | Unknown edge types are refused. |
| Hydration round-trip | Every ingested envelope re-hydrates byte-identically. |
| Confidence stamp consistency | Stamped vs. recomputed mismatch raises a finding. |
| Surface enforcement | NAV-bearing payload without surface fields refused. |
| Compatibility-matrix queries | `is_op_permitted(surface_a, surface_b)` returns correct compatibility class. |
| Supersession resolution | Latest non-superseded canonical at present; correct pre-anchor resolution at `T_anchor`. |
| Orphan detection | Orphan ingestion raises finding; retained orphan capped at `LOW`. |
| Invalidation propagation | Downstream confidence flooring on parent invalidation. |
| Rebuild determinism | From-scratch rebuilds are byte-identical (modulo encoding). |
| Incremental drift detection | Shadow rebuild diff raises `REGISTRY_INCREMENTAL_DRIFT`. |
| UTC discipline | Non-UTC ingest refused. |
| Visibility fencing | Objects with `indexed_at > T_anchor` fenced out even when `as_of <= T_anchor`. |
| Closed-enumeration enforcement | Unknown enum values refused; known set frozen against v1. |

Every test MUST be deterministic and reproducible.

## 15. Replay-Stability Requirements

The registry MUST satisfy the replay invariants per SEM-006 §5 and
SEM-008 §8:

- RP-001. For any deterministic-chain object, registry state at any
  later moment MUST permit byte-identical replay of the object.
- RP-002. For any non-deterministic object with intact
  `source_state_hash`, the registry MUST permit identical replay.
- RP-003. For any historical replay query, the registry MUST be able to
  identify whether replay is `GUARANTEED`, `BEST_EFFORT`, or
  `UNREPLAYABLE`, with reasons.
- RP-004. Cross-migration replays MUST dispatch each input under the
  schema version in force at its `produced_at`.
- RP-005. Replay outputs MUST themselves be recorded as `ReplayRun`
  objects; the registry MUST maintain replay history queryable by
  target `object_id`.

Failure of any replay invariant MUST be surfaced as `REPLAY_FAILURE`
finding with severity proportionate to the affected artifact's
governance and confidence.

## 16. Enforcement Surface

| Component | Enforcement |
|---|---|
| Ingestion layer | Apply §3, §5, §7, §8, §10, §11, §12 invariants at every insert. |
| Retrieval layer | Apply §3.2 validation; surface §6 confidence chain; recompute §8 staleness; resolve §10 supersession. |
| Audit subsystem | Run §4.3 shadow rebuild on schedule; emit §13 violation findings; surface §9 orphans. |
| Replay subsystem | Maintain §15 history; refuse §15 violations. |
| Schema registry | Maintain §2.3 schema uniqueness; refuse cross-MAJOR coercion (SEM-008). |
